# Этап 4. MVP-оркестратор и тестирование

Risk Orchestrator — локальный стенд для управления расчётами рисков. Через веб-интерфейс можно подать заявку, увидеть причину ожидания, провести расчёт через согласование до публикации. У каждого исполнения есть идентификатор RUN; несколько заявок на одинаковый расчёт могут получить один RUN.

## Запуск

**Для показа на Windows откройте [Запустить.cmd](Запустить.cmd).** Понадобится Python с pip (проверено на Python 3.12). При первом запуске скрипт при необходимости установит FastAPI и Uvicorn из PyPI в локальную папку `.runtime`. Команды ниже выполняются из папки этапа 4, где лежит этот README.

```powershell
python start.py --open
```

Браузер откроется автоматически. Сервер начинает поиск порта с `127.0.0.1:8766`, при занятости проверяет следующие порты до `8775`. Фактический адрес выводится в терминале. Если все порты диапазона заняты, выполните `python start.py --port 0 --open`. Чтобы остановить приложение, нажмите Ctrl+C в терминале сервера.

База `data/stage4.sqlite3` создаётся при первом запуске. История сохраняется между показами. Для репетиции с отдельной базой выполните `python start.py --db data/rehearsal.sqlite3 --open`.

## Роли

| Роль | Что показать |
|---|---|
| Администратор | Запуск демо, общая очередь, занятые ресурсы, хронология и журнал всех запусков |
| Аналитик | Подача заявки с бизнес-датой и предшественником, просмотр своих запусков |
| Риск-менеджер | Просмотр процесса, бизнес-даты и инициатора. Можно согласовать расчёт или вернуть её с комментарием |
| Директор | Просмотр запуска и комментария риск-менеджера. Утверждение публикует результат |

## Показ порядка выполнения

В роли администратора выберите сценарий рядом с кнопкой **Запустить демо**. Во вкладке **Демонстрации** все запуски выбранной партии видны на общей шкале времени. Жёлтая полоса показывает ожидание допуска, фиолетовая — выполнение. Справа остаётся последняя причина ожидания даже после публикации результата. Под таблицей находится журнал этой партии, а по клику на RUN открывается подробная история. Список **История демонстраций** позволяет вернуться к завершённому показу.

| Сценарий | Заявки → запуски | Что наблюдать |
|---|---|---|
| Чтение и запись | 4 → 3 | Совместимое чтение, дубль от регламента и ожидание записи |
| Закрытие трёх дат | 12 → 12 | На каждой дате загрузка сделок предшествует загрузке курсов, затем запускаются два расчёта. Независимые даты обрабатываются параллельно |
| Пиковая нагрузка | 18 → 12 | Шесть дублей объединяются. На шести датах одновременно заняты до четырёх слотов, остальные запуски ждут исполнителя |
| Возврат на перерасчёт | 2 → 2 при старте; 3 → 3 после возврата | Расчёт Анны, обновление общего справочника, возврат риск-менеджером и публикация директором |
| Общий справочник | 9 → 9 | После четырёх читателей писатель обновляет общий справочник. Следующие четыре расчёта используют обновлённый справочник |

1. Выберите **Чтение и запись** и нажмите **Запустить демо**. Два идентичных обращения от Анны и регламента получат общий запуск кредитного расчёта. Каждая следующая демонстрация использует новые бизнес-даты.
2. Откройте **Очередь** и нажмите на причину ожидания загрузки сделок. Откроется карточка блокирующего RUN. В таблице **Области доступа** найдите сделки: в строке указаны дата и режим чтения. Ссылка доступна, когда роль может открыть этот RUN. При занятой мощности без конкретного блокирующего запуска причина остаётся текстом.
3. Откройте **Хронология**. По времени старта и окончания видно, что загрузка началась после обоих читателей. Нажмите на RUN, чтобы увидеть результат расчёта и историю допуска. По умолчанию расчёт длится примерно четыре секунды.
4. Для маршрута с согласованием выберите роль **Аналитик**, нажмите **Запустить процесс** и запустите кредитный расчёт. После вычисления исполнитель освободит блокировки. Выберите **Риск-менеджер → Согласования**, откройте нужный RUN и одобрите его. Затем выберите **Директор**, откройте тот же RUN и подтвердите публикацию. Администратор увидит оба решения в журнале.
5. Для проверки отказа верните расчёт на перерасчёт с комментарием. В уведомлении появится номер нового RUN. В карточках исходного запуска и перерасчёта видна их связь. Переход между ними доступен пользователю, который может открыть обе карточки.

В сценарии **Возврат на перерасчёт** сначала дождитесь завершения RUN обновления справочника. Переключитесь на риск-менеджера, откройте кредитный расчёт этой партии и верните его с комментарием. Когда появится новый RUN, согласуйте его. В роли директора утвердите этот же RUN. В истории демонстраций администратор увидит оба запуска и события публикации.

Если исполнитель остановлен, индикатор становится жёлтым. API продолжает показывать состояние и историю; для возобновления фоновой обработки перезапустите стенд. Красный индикатор означает потерю связи с API.

## Устройство стенда

| Файл | Ответственность |
|---|---|
| backend/app.py | FastAPI, команды интерфейса, представления для ролей, запуск и остановка worker |
| backend/orchestrator/worker.py | Отдельный процесс для допуска, исполнения и продления срока владения ресурсами |
| backend/orchestrator/engine.py | Заявки, дедупликация, очередь, зависимости, согласования и аудит |
| backend/orchestrator/calculations.py | Детерминированные вычисления по данным на момент запуска |
| backend/orchestrator/scenarios.py | Состав демонстрационных партий |
| backend/database/ | Подключения SQLite, схема, транзакции состояния и журнал событий |
| backend/tests/ | Тесты оркестратора и слоя базы данных |
| tests/ | Браузерная проверка интерфейса |
| frontend/ (index.html, style.css, app.js) | Браузерный интерфейс, отправка команд и чтение состояния через HTTP |

Стенд реализован как модульный монолит. API и фоновый исполнитель работают отдельными процессами с общей базой SQLite. Оркестратор записывает заявки, исполнения этапов, блокировки, решения и события в связанные таблицы SQLite в одной транзакции. Проверка конфликтов и захват ресурсов происходят в одной транзакции. Исполнитель обрабатывает до четырёх RUN одновременно и освобождает ресурсы по окончании расчёта, до решения человека. Ошибка исполнения и повторная попытка фиксируются в истории RUN.

Для сделок и курсов учитывается бизнес-дата: зависимый процесс за другую дату ждёт завершения предшественника и читает свою партицию. У общего справочника единая область для всех дат. Решения принимаются по номеру запуска. При возврате на перерасчёт создаётся новый RUN, связанный с исходным.

Роли переключаются для локальной демонстрации и сохраняются в cookie браузера. Для одновременного показа разных ролей используйте отдельные профили или обычное и приватное окна. Сервер слушает loopback-адрес. Стенд использует синтетические данные и учебную идентификацию пользователей.

### Как устроена база

Шаблоны и этапы хранятся в `business_process` и `stage`. Каждому отдельному обращению соответствует строка `bp_request`. Дубликат получает статус `merged` и ссылку на исходную заявку. Её маршрут выполняется один раз. Ключ команды в `request_receipt` позволяет безопасно повторить HTTP-запрос.

В интерфейсе номер RUN обозначает весь процесс от заявки до публикации. Таблица `workflow` связывает этот стабильный номер с исходной заявкой. У каждого этапа есть своя `stage_request`, а после допуска — запись исполнения в `run`. Одобрение риск-менеджером и утверждение директором отражаются в отдельных этапах. Таблицы `lock` и `event` хранят владение ресурсами и аудит. У каждого запуска один результат в `run_result`, ссылки на опубликованные результаты — в `published_result`. Для расписания, решений и партий демонстраций предусмотрены отдельные таблицы.

При переходе со старой версии остановите старый сервер и worker, затем запустите новую версию с прежним файлом базы. При первом открытии она перенесёт данные из `ledger`, прочитает их обратно и сверит состояние. Только после совпадения удаляется старая таблица. При ошибке SQLite откатывает перенос. Старый исполняемый код следует использовать только с копией базы до перехода.

## Проверка

### Тесты бэкенда

```powershell
python -m pip install -r requirements.txt pytest
python -m pytest backend/tests -q
```

Набор проверяет схему SQLite, доступ к данным, очередь, блокировки, совместимость областей данных, обработку ошибок, результаты и двухэтапную публикацию.

### Браузерные тесты

Для браузерного теста нужны Python с pip и Node.js 20 или новее с npm. В корне этапа выполните:

```sh
npm ci
npm run browser:install
npm run test:ui
```

`npm ci` устанавливает Playwright 1.62.1 и зависимости по `package-lock.json`. Вторая команда загружает Chromium. Для следующих прогонов достаточно `npm run test:ui`. Тест сам запускает API и worker на временной базе. Для обычного показа стенда достаточно Python.

Для проверки в установленном Edge вместо загрузки Chromium укажите путь к нему в PowerShell:

```powershell
$env:TEST_BROWSER = "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe"
npm run test:ui
```

Если Python отсутствует в PATH, задайте `TEST_PYTHON` с полным путём к `python.exe`. По умолчанию браузерный тест обновляет материалы в папке **Демонстрация**. Для записи в другую папку задайте `TEST_OUTPUT`.

В браузерном тесте проверяются все пять сценариев. Для цепочек сравниваются время окончания предшественника и время допуска потомка. Для пиковой нагрузки проверяется максимум из четырёх одновременных исполнений, для общего справочника — использование последними четырьмя расчётами результата обновления. Фактические события четырёх расширенных сценариев сохраняются в [протоколе сценариев](Демонстрация/протоколы/Сценарии.json). Тестовая длительность синтетического расчёта — две секунды.

В папке **Демонстрация** находятся [протокол прогона](Демонстрация/протоколы/Протокол.json), [снимок ожидания ресурса](<Демонстрация/скриншоты/01 — Ожидание ресурса.png>) и [хронология](<Демонстрация/скриншоты/02 — Порядок выполнения.png>). При повторном запуске браузерного теста эти материалы обновляются.

### Нагрузочная проверка через HTTP

```powershell
python -B tests/load_http.py
```

Тест поднимает отдельный сервер с временной базой. Сто клиентов одновременно вызывают `POST /api/run` для двадцати бизнес-дат, по пять заявок с разными ключами на каждую дату. Искусственная длительность расчёта — 3 секунды.

| Метрика | Результат локального прогона 24.11.2026 |
|---|---:|
| Успешные ответы | 100 из 100 |
| Расчёты, дошедшие до согласования | 20 |
| Заявки, присоединённые к другим запускам | 80 |
| Пик одновременно выполняющихся RUN | 4 |
| Время регистрации заявки: медиана / p95 / максимум | 135,4 / 206,4 / 219,9 мс |

Время регистрации измеряется на клиенте от отправки заявки до ответа API. Пик исполнения определяется по пересечению серверных интервалов расчёта. При повторном прогоне измерения сохраняются в [протоколе нагрузки](<Демонстрация/протоколы/Нагрузка HTTP.json>).
