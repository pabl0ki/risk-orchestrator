# Этап 4. MVP-оркестратор и тестирование

Стенд выполняет расчёты по восьми синтетическим строкам, сохраняет версии результатов в SQLite и показывает порядок допуска через веб-интерфейс в оформлении этапа 3.

## Запуск

В Windows откройте **Запустить.cmd**. При первом запуске нужен Python с pip и доступ к PyPI для установки FastAPI и Uvicorn. Проверено на Python 3.12. Запуск из терминала в этой папке — `python start.py --open`. Адрес по умолчанию — http://127.0.0.1:8766. Чтобы остановить приложение, нажмите Ctrl+C в терминале сервера.

История сохраняется в `stage4.sqlite3`. Для отдельного показа можно указать другой файл командой `python start.py --db rehearsal.sqlite3 --open`.

## Показ порядка выполнения

В роли администратора выберите сценарий рядом с кнопкой **Запустить демо**. Во вкладке **Демонстрации** все запуски выбранной партии видны на общей шкале времени. Жёлтая полоса показывает ожидание допуска, фиолетовая — выполнение. Справа остаётся последняя причина ожидания даже после публикации результата. Под таблицей находится журнал этой партии, а по клику на RUN открывается подробная история. Список **История демонстраций** позволяет вернуться к завершённому показу.

| Сценарий | Заявки → запуски | Что наблюдать |
|---|---|---|
| Чтение и запись | 4 → 3 | Совместимое чтение, дубль от регламента и ожидание записи |
| Закрытие трёх дат | 12 → 12 | На каждой дате загрузка сделок предшествует загрузке курсов, затем запускаются два расчёта. Независимые даты обрабатываются параллельно |
| Пиковая нагрузка | 18 → 12 | Шесть дублей объединяются. На шести датах одновременно заняты до четырёх слотов, остальные запуски ждут исполнителя |
| Общий справочник | 9 → 9 | После четырёх читателей писатель обновляет общий справочник. Следующие четыре расчёта закрепляют новую входную версию |

1. Выберите **Чтение и запись** и нажмите **Запустить демо**. Два идентичных обращения от Анны и регламента получат общий запуск кредитного расчёта. Каждая следующая демонстрация использует новые бизнес-даты.
2. Откройте **Ресурсы**. Кредитный и рыночный расчёты одновременно читают сделки одной даты и записывают результаты в разные области. Во вкладке **Очередь** загрузка сделок ожидает освобождения ресурса для записи.
3. Откройте **Хронология**. По времени старта и окончания видно, что загрузка началась после обоих читателей. Нажмите на RUN, чтобы увидеть версию результата, значения строк, входные версии и историю допуска. По умолчанию расчёт длится примерно четыре секунды.
4. Для маршрута с согласованием выберите роль **Аналитик**, нажмите **Запустить процесс** и запустите кредитный расчёт. После вычисления результат получит версию и освободит блокировки. Выберите **Риск-менеджер → Согласования**, откройте нужный RUN и одобрите его. Затем выберите **Директор**, откройте тот же RUN и подтвердите публикацию. Администратор увидит оба решения в журнале.
5. Для проверки отказа верните версию на перерасчёт с комментарием. В базе появится новый запуск, а причина отказа останется в истории предыдущего.

## Устройство стенда

| Файл | Ответственность |
|---|---|
| app.py | FastAPI, команды интерфейса, представления для ролей, запуск и остановка worker |
| worker.py | Отдельный процесс для допуска, исполнения и продления срока владения ресурсами |
| engine.py | Транзакции SQLite, заявки, дедупликация, очередь, зависимости, версии, согласования и аудит |
| calculations.py | Детерминированные вычисления по закреплённым входным версиям |
| index.html, style.css, app.js | Браузерный интерфейс, отправка команд и чтение состояния через HTTP |

У API и worker одна кодовая база и одна SQLite. Одна транзакция объединяет проверку конфликтов с выдачей всех разрешений. Долгое вычисление происходит после фиксации этой транзакции. После возврата человека к карточке сервер повторно проверяет этап и актуальность версии перед одобрением.

Роли переключаются для локальной демонстрации и сохраняются в cookie браузера. Для одновременного показа разных ролей используйте отдельные профили или обычное и приватное окна. Сервер слушает loopback-адрес. Стенд использует синтетические данные и учебную идентификацию пользователей.

## Проверка

- `python -B -m unittest -v test_engine` — 20 тестов, включая совместимое чтение, конфликт записи, присоединение дублей, восстановление после истечения блокировки, повтор команды и двухэтапную публикацию.
- `node test_ui.cjs` — сквозной тест на отдельной временной базе. Требуются Node.js, Playwright и Chromium или Edge. Переменные TEST_PYTHON и TEST_BROWSER позволяют выбрать исполняемые файлы. Скрипт поднимает API и worker и выполняет команды через браузер.

В браузерном тесте проверяются все четыре сценария. Для цепочек сравниваются время окончания предшественника и время допуска потомка. Для пиковой нагрузки проверяется максимум из четырёх одновременных исполнений, для общего справочника — совпадение входной версии последних четырёх расчётов с версией, созданной обновлением. Фактические события трёх расширенных сценариев сохраняются в [протоколе сценариев](Демонстрация/Сценарии.json). Тестовая длительность синтетического расчёта — две секунды.

В папке **Демонстрация** находятся [протокол прогона](Демонстрация/Протокол.json), [снимок ожидания ресурса](<Демонстрация/01 — Ожидание ресурса.png>) и [хронология](<Демонстрация/02 — Порядок выполнения.png>). При повторном запуске браузерного теста эти материалы обновляются.
